# Production implementation and release runbook

This replaces the historical short storefront implementation phases as the production checklist. The repository now implements the commerce core and supervised operations, but **production launch is not verified**. There are no Turso/Vercel credentials or linked Vercel project available in this workspace. No production data was imported, no external messages were sent, and no paid infrastructure was provisioned.

## Implemented architecture

- Express serves the existing Arabic RTL storefront and authenticated administration. The web process does not start campaigns, run agents, or open the old shared SQLite file. Only `/assets` is served statically; repository files and sector catalogs are not public downloads.
- `store_data.js` owns the retail catalog, customers and orders. Local development uses a dedicated `.runtime/commerce.db` through `sql.js`, with synchronous atomic persistence and a process lock. Turso uses the JavaScript web client. `NODE_ENV=production` or `VERCEL` forbids local fallback, including partially configured Turso credentials. Local server and worker processes must not share a sql.js file: configure a development Turso database for multiprocess testing.
- Versioned migrations are transactional, repeatable and available through `npm run db:migrate`. Startup retains compatibility by applying missing versions; deploy migrations before promoting a release. Catalog seeding inserts missing IDs without replacing staff changes.
- Commerce transactions re-read current active products, validate variants and stock, snapshot integer piastre prices and totals, reserve stock, and insert order events into the same database transaction. A fixed delivery fee is configured in piastres using `SHIPPING_FEE_MINOR`; set it explicitly, including `0` for free delivery. Discounts, regional shipping and online payments are not enabled.
- Browser checkout obtains a server quote, sends the expected total, and keeps its idempotency key through ambiguous network failures. A changed total requires review. Reusing a key for different normalized customer/order details returns 409. A successful replay returns the original order reference and total.
- Separate workers claim durable jobs using leases, fence acknowledgements with lease tokens, retry with backoff and move poison jobs to dead letters after five attempts. Paused agents keep their jobs without exhausting retries. Reservations expire after 24 hours unless staff confirm them. Confirmed orders retain stock until cancellation or shipment. Workers publish heartbeat timestamps for operations monitoring.
- The deployment includes a protected Vercel Cron route at `/api/cron/worker`, scheduled once daily at 07:00 UTC to support the Hobby plan. Hobby execution can occur within that hour; this is not a real-time worker. It performs a bounded pass of at most ten durable jobs, maintenance and one delivery attempt per supported channel, then exits. Set a secret `CRON_SECRET` in Vercel. For frequent processing, use a dedicated worker or an eligible Vercel plan with a more frequent schedule. The dashboard heartbeat will become stale between daily runs; it does not establish that the daily cron failed. WhatsApp Web still needs its standalone sender.
- Individual staff accounts use scrypt passwords, encrypted TOTP secrets, replay protection, revocable eight-hour sessions, CSRF tokens and role permissions. The old shared-password administrator login is removed. Bootstrap accounts through the CLI; support has support/recovery access, operations has orders/inventory access, and admins have all permissions.
- Customer accounts retain guest checkout and signed sessions. Password recovery requires staff identity verification, a reference recorded in the audit log, and delivery of a single-use 15-minute token through a verified channel. Reset invalidates existing sessions. There is no SMS/identity provider integration.
- Catalog APIs have a five-second process cache and up to ten seconds of public CDN caching; stock display can lag, but checkout always checks the authoritative database. Customer, staff, tracking and checkout responses use `no-store`.

## Agent authority and remaining integrations

The coordinator manages inventory recommendations, order confirmation proposals, support drafts and sector-specific campaign starter proposals. All actions require staff approval; the global control starts paused until an administrator enables it from the agents page. Inventory/order/marketing agents use deterministic rules. Approving a marketing proposal atomically saves it as a campaign draft; it does not send messages. Support can optionally use the OpenAI Responses API with strict structured output, no tools, no response storage, a 20-second timeout and a daily call budget. `AI_ENABLED=false` and `AI_DAILY_CALL_LIMIT=0` are the defaults. A model must be selected explicitly with `OPENAI_MODEL`; no paid API calls occur during tests. Admins can inspect agent state, task evidence/proposals, review decisions, audit history and worker queue status at `/store/agents`; the UI is limited to the newest 100 tasks and audit entries.

From each agent card, administrators can open **خصائص الوكيل** and save non-secret operating limits in the database. Every agent has a daily proposal cap; configurable agents also expose their post times, outreach batch size, lead-cleanup bounds, low-stock threshold, or Shopify polling interval. These changes are audited and take effect without a code deployment. Provider tokens, SMTP passwords, and OpenAI keys remain environment/secret-manager settings and are never exposed in the dashboard.

Customer text is withheld from the model by default. Enabling `AI_ALLOW_CUSTOMER_TEXT=true` sends bounded text with phone/email/link redaction; names and other identifying information may remain, so this requires an approved data-processing policy. Staff must review every draft for correctness and inappropriate commitments. References: [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

There is no agent tool for purchasing, refunds, sending messages or changing prices. Approved support drafts and inventory suggestions are retained for staff to act on. Model outages leave tickets visible for manual support and jobs retryable. Agent output cannot select tools, change permissions or bypass approval. The kill switch blocks subsequent agent dispatch; an already executing database transaction may complete.

The legacy public campaign, offer and support-chat endpoints return 410. Standalone campaign scripts are retained as development tools and are not production dependencies. Their existing dependency vulnerabilities and behaviors must be reviewed before any separate use. New outreach integrations must use `lib/outreach-policy.js` with shared, transactional contact history, opt-out and batch accounting, consent, Cairo working hours, the 30-day rule, Friday closure and the WhatsApp rest interval. No production messaging adapter or webhook is enabled. This avoids duplicating outreach before consent and provider requirements are verified.

Affiliate rates and commission settlement rules are not numerically specified in the current business specifications. Legacy affiliate balances are preserved in the migration archive; automatic attribution, commission calculation and payouts remain disabled pending a reconciled ledger and approved rates. Carrier APIs, financial refunds, online payment webhooks and broader AI autonomy remain later milestones.

## Development and verification

1. Use Node 22.20+ and run `npm ci --ignore-scripts`. Copy `.env.example` to a private `.env` and set the customer session secret and staff MFA key to separate random values of at least 32 characters. Set the delivery fee. Ignore files cover runtime data, environment secrets and backups.
2. Run `npm run db:migrate`. Set the temporary `BOOTSTRAP_STAFF_*` environment variables, including a 14+ character password and a 32+ character base32 authenticator secret. Enroll the secret in the employee's authenticator through a secure channel, run `npm run staff:create`, then remove the bootstrap variables. Keep `STAFF_MFA_KEY` stable and backed up separately from the database.
3. Run `npm start`, open `/store/admin`, and sign in with email/password/TOTP. The management overview is `/store/manager`, agent monitoring is `/store/agents`, and the current campaign workspace is `/store/campaigns` (also `/store/marketing`). Current campaigns start empty and appear after a staff member saves a draft or approves a marketing proposal; historical campaign records are separate at `/store/campaign-history` and require an explicit legacy database import. Enter **verified actual stock** at `/store/operations`; every product starts at zero stock. Product variants share the product's inventory pool. Reconcile a physical return before staff change an order to `returned`.
4. Use separate development Turso credentials before starting `npm run worker`. Never run standalone legacy campaigns as part of the commerce service.
5. Run `npm run check`, `npm test` and `npm run rehearse`. The rehearsal uses only an in-memory store, synthetic orders and a local HTTP server. It does not establish production performance. `LOAD_TEST_URL` with `npm run load:test` probes catalog requests on staging; checkout service concurrency is measured separately by the rehearsal.
   The optional isolated Turso test runs only when `TEST_TURSO_DATABASE_URL` and `TEST_TURSO_AUTH_TOKEN` identify a disposable staging database. It creates and removes a uniquely named verification table; never point these variables at the live production database.
6. CI runs syntax/bundle checks, tests and a production dependency audit. Legacy development tools are excluded from production installs. The Blob OIDC helper is pinned to compatible 3.5.0 to avoid the audited vulnerable CLI-config dependency chain; verify actual Blob uploads and OIDC behavior in staging before release, and review removal of the pin when upstream dependencies are fixed.

## Data migration and recovery

Run imports only on a fresh, backed-up destination after disabling writes and workers. Always rehearse on staging first.

```text
npm run db:import -- path/to/source.db
npm run db:import -- path/to/source.db --apply
```

Dry-run reports source checksum, table counts and order totals without importing records. Apply requires no existing destination orders/customers or staff catalog edits; it is transactional and replayable by source checksum. Retail tables import into the commerce schema. Legacy affiliates, contact history and other business tables are retained in `legacy_records` without exposing them to public APIs. Imported customers have sessions invalidated. Historical orders receive integer totals and `stock_state=legacy`, with no inferred stock movement. Reconcile all totals, historical statuses, catalog prices, affiliate balances and contact history before activating any integration. Imported cash collections and refunds are not inferred.

```text
npm run backup -- backups/commerce.encrypted.json
npm run restore:check -- backups/commerce.encrypted.json .runtime/isolated-restore.db
```

Backups take a consistent transactional snapshot and encrypt it with AES-256-GCM using `BACKUP_ENCRYPTION_KEY`. Restore validates authentication, recreates schema, reconciles row counts and runs SQLite integrity checks. It refuses to overwrite an existing destination. Backups contain customer data and staff hashes; retain encryption and MFA keys separately in the secret vault. The GitHub backup workflow runs daily and verifies an isolated restore; configure production environment secrets, artifact access, failure notifications and independent off-platform backup copies before relying on it. A workflow that has not run successfully does not meet the RPO.

For a live incident: pause agents, stop workers and writes, preserve the current database, inspect the backup with isolated restore, and use the provider's verified restore/import procedure into a **new Turso database**. Reconcile records since the snapshot, update credentials, validate staff access/stock/orders and only then resume writes and workers. The application does not overwrite a live cloud database automatically. Rehearse this procedure with the actual provider and prove RPO <=24 hours / RTO <=4 hours.

## Deployment sequence and launch blockers

1. **Provision staging:** link the intended repository to an isolated Vercel staging project, create a staging Turso database and Blob store, and provision a separate container worker using `Dockerfile`. Set the same Turso credentials on web and worker, with separate environment secrets from production. Start with one worker; increase only after measuring transaction contention. Vercel has finite function durations, so persistent workers remain separate. [Vercel limits](https://vercel.com/docs/functions/limitations)
2. **Configure:** set `NODE_ENV=production`, Turso credentials, `BASE_URL` to the exact HTTPS staging origin, the customer session secret, `STAFF_MFA_KEY` and `SHIPPING_FEE_MINOR`. Connect Blob OIDC or its scoped token. Bootstrap staff securely. Set backup credentials only in the backup runner. Keep AI disabled until its provider, model, budget and data policy are approved. Configure the production domain separately from preview URLs; mutations require the configured origin.
3. **Migrate and test staging:** take a verified source backup, run migrations and a dry-run import, apply/reconcile the import if appropriate, enter verified inventory and start the worker. Exercise real Turso concurrent checkout, transactions, outage/recovery, worker restart, Blob upload, cookie behavior, mobile/RTL accessibility, password recovery and an actual carrier/COD operating procedure. Do not use real customer data in general test fixtures.
4. **Provision production:** create separate production Turso/Blob/Vercel resources and worker secrets. Confirm region latency, quotas, cost limits and backup retention. Set named owners for incidents, fulfillment, cash reconciliation, support and agent review. Configure HTTPS and Vercel project protection so preview/staff tools are not accidentally exposed through deployment settings.
5. **Release:** require passing CI and security review, a successful production-provider restore rehearsal, reconciled migration totals and stock, staff MFA, delivery fee confirmation, and external monitoring. Freeze old writes for cutover, back up, apply additive migrations/imports, deploy compatible worker/web releases, and smoke-test one controlled order. Verify queue heartbeat, inventory, delivery totals, tracking privacy and cash reconciliation. Pilot with a small customer group before broader traffic.
6. **Monitor:** alert externally on readiness failures, elevated 5xx/checkout failures, worker heartbeat older than two minutes, queue age over five minutes, any dead letters, stock discrepancies and backup failures. Track AI calls and provider budgets. Alert ownership and delivery still require configuration with the operations team. Target availability 99.9%, cached catalog p95 <500 ms and checkout API p95 <2 s at 100 shoppers; measure these on production-like infrastructure and set independent synthetic checks.
7. **Rollback:** pause agents and stop affected workers; redeploy the prior **compatible** web/worker artifact and preserve committed orders. Do not blindly roll back to the legacy checkout, which bypasses the new stock and idempotency invariants. Schema changes are additive; fix forward where possible. Restore data only after write freeze and explicit reconciliation, following the recovery procedure above.

No live resources, rollout, production load test or provider restore have been performed in this workspace. Browser visual QA was blocked by unavailable browser access and native-app approval timeout. HTTP routes, inline script compilation, concurrency, recovery, migration replay, MFA/CSRF/RBAC and the encrypted local restore are covered by automated tests. Those checks support the code changes; they do not authorize a claim that the full production launch is complete.
